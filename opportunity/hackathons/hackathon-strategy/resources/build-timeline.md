# Hackathon build timeline

A schedule that protects the two things that lose winnable hackathons: not having
a working demo, and the last-hour collapse. Adapt the proportions to the event
length; the shape is constant.

## The shape (as fractions of the total time)

```
first third      SKELETON
  a working end-to-end path, however thin: something that runs and can be demoed.
  If everything else failed from here, you would still have a demo. This is the
  most important milestone and the one teams skip by building components in
  isolation that only integrate at the end (and then do not).

middle third     DEEPEN
  from the skeleton, add depth to the parts that score on the heavy rubric
  criteria, in priority order. Every increment leaves the demo still working.
  Touch the optional features only if the core is solid.

~last quarter    FREEZE and POLISH
  a hard stop on new features. From here: fix what breaks, polish the demo surface,
  handle the edge cases the judges might hit. Reaching for one more feature now is
  how a working project becomes a broken one at the deadline.

final buffer     SUBMIT
  reserved, and always needed: record the demo video, complete the submission
  form, write the required statements, re-read the requirements for anything
  missed, rehearse the pitch. All of this takes longer than expected.
```

## The rules

- The skeleton milestone is non-negotiable. A demoable thin slice by the end of
  the first third is worth more than sophisticated components that have not been
  integrated.
- The demo path is the working path. Never let the fragile feature be the one on
  stage.
- The freeze is a real stop, on the clock, agreed in advance. After it, no new
  features, only landing and polish.
- The submission buffer is protected. A brilliant project not submitted correctly
  scores zero; a required field missed can disqualify.

## The failure this prevents
The classic loss: a team integrates at the deadline, the demo breaks on stage, and
an ambitious project places below a simple one that ran. This timeline makes the
working demo the earliest milestone and the submission the safest, so the team
always has something to show and always submits it correctly.
